**W3 scope — only this (spec F3, F4, F5, F7; cap per F6 as reconciled above):**

1. **Server-persisted drafts.** Parsing a complete draft now persists it server-side under an unguessable draft ID. Storage follows spec Section 5 (server memory + JSON persistence, or KV-equivalent on Workers), holds only drafts and audit records — never credentials — and sits behind a small storage interface so the W4 deployment step can swap the backing store without touching flow logic. No D1 unless you hit a concrete blocker; if you do, stop and report it as a batched question instead of adopting D1 silently. The frozen archive's D1 store stays unported.
2. **Confirmation card (F3, the core UI).** The draft opens on a card showing payee name/email, line items, currency, total, note, model confidence (labelled as an uncalibrated estimate), ambiguity warnings, and any `injection_flags` prominently. Fields are editable. The card states "DRAFT — not paid" until execution completes. Assembled workspace layout per spec Section 5: input/clarification on one side, card and status on the other, audit list below or in a side column; standing design constraints apply (restrained editorial style, semantic HTML, keyboard operable, visible focus, reduced-motion, SSR-safe, mobile usable, no unnecessary libraries). The W1 manual form remains available and unchanged as a fallback path; it is not the W3 flow.
3. **Confirm means server re-validation (F4).** The confirm action submits only the draft ID plus the user's edits. The server retrieves the stored draft by ID, applies edits, and re-validates everything server-side: schema, total recomputed from line items (mismatch flags the card and blocks confirmation), payee email well-formed (an empty email must be filled on the card before confirmation can proceed), and the amount cap. **A tampered client payload can never change what the server executes beyond the validated edits** — amounts/payees are executed exactly as re-validated from the stored draft plus edits, never as raw posted totals. Only after re-validation passes does the server create the PayPal order (intent=CAPTURE, return/cancel URLs at this app), reusing the W1 PayPal service, `flow.ts` reconciliation, and `custom_id` signing: redirect to sandbox approval → return → GET → capture only if APPROVED → GET again → status shows COMPLETED + transaction ID only on verified completion.
4. **Amount cap (F6 safety half).** Default USD 200, configurable via the amount-cap variable already listed in `.env.example` since repo creation — use that existing variable name; if it is somehow absent, stop and report rather than inventing a parallel name. Enforced twice: the card visibly marks an over-cap draft and blocks its confirmation, and the server re-validation blocks it again independently (including when the confirm request is crafted directly, bypassing the UI). An over-cap block creates **no PayPal order**, is stated in plain language with the cap and the attempted amount, and is recorded in the audit trail as BLOCKED with its reason.
5. **Audit trail (F5).** Every intent is logged and listed in the UI: raw input, AI draft, user-confirmed (edited) version, order ID when one exists, and status transitions DRAFT → CREATED → APPROVED → COMPLETED, or BLOCKED / CANCELLED. Server-persisted; survives page refresh and dev-server restart (state the backing store and its limits honestly in the README — e.g. if local JSON persistence is used, say so). Cancelled checkouts record CANCELLED and never capture, reusing the W1 cancel semantics.
6. **Errors (F7).** Every PayPal/LLM/storage failure surfaces in plain language (stage + original error code) at the point it occurs. No blank pages, no fake success, no silent draft loss: if execution fails after confirmation, the audit record shows the failure stage.
